# 我的贡献：把 AI 质量问题变成可执行的工程工作

## 我解决的问题

连续音频系统并不缺少可以概括的内容，真正困难的是判断“哪些内容可以写成这个用户的记录”。如果只追求摘要流畅，下游生成模型会将片段中的故事、别人的表达或模糊线索补成完整叙事。

我的工作从这些实际质量问题出发，连接产品目标、算法行为、数据证据和工程验证。核心不是提出更多抽象原则，而是让每一个问题都有对应的观察位置、评估方法和处理方案。

## 六类具体工作

| 工作 | 我的具体动作 | 形成的产出 |
|---|---|---|
| 系统梳理 | 阅读音频算法、事件生成与记忆实验的资料，整理模块职责和数据依赖 | 系统流程说明与交互式地图 |
| 问题定义 | 把媒体污染、错归和无证据生成拆成不同质量目标 | 标签口径、错误分类和验收问题 |
| 实验设计 | 固定样本与映射，保留原始基线，控制每轮变化，安排消融和重复运行 | 版本比较、实验配置与结论记录 |
| 工具实现 | 编写批量运行、指标分析和复核页面，处理缓存、重试和标签导出 | 可反复使用的实验与人工复核工具 |
| 根因定位 | 将最终卡片追溯到引用事件、输入片段和上游判断 | 跨层血缘、误差分布与定位结果 |
| 方案交接 | 整理最小修改、验证结果、已知问题及后续检查项 | 可审阅的候选方案与交接材料 |

## 我的工作流程

### 1. 把反馈改写成一个可以测试的问题

例如，“AI 写得不对”过于宽泛。我会进一步区分：录音是否存在、是否转录错误、是不是媒体内容、是否认错说话人、是否把弱线索写成确定事实。这样才能判断应该检查哪一层，而不是直接修改最后的生成提示。

### 2. 先建立观察手段

在连续音频任务里，单独查看一个 JSON 或一句摘要通常不足以判断。我将音频、转录、预测与人工标签组织在同一个复核流程中，并让卡片能够反查来源事件。工具先把问题展示清楚，方案讨论才有依据。

### 3. 一次验证一个主要假设

面对媒体误判，我分别验证转录依赖、判断规则、声学线索和集成方式。每次比较同时看修复了哪些错误、增加了哪些新错误，而不是只选择最好看的单个数值。

### 4. 将候选带到下游再验证

片段判断改变后，事件集合和生成主题可能一起变化。我用最终卡片检查候选的产品效果，把局部收益与整体表现联系起来。

### 5. 留下可以接手的结果

一个候选方案需要同时带有改动内容、输入集合、比较结果、指标口径和已知残余问题。我把这些内容组织成资料和页面，便于后续人员理解“为什么这样改”和“怎样判断是否有效”。

## 项目体现的能力

- **AI 产品判断**：把模糊体验问题转成清晰的模型目标、产品动作和质量指标。
- **实验与数据能力**：识别样本对齐、标签变更、随机性和评估目标不一致带来的误导。
- **AI 应用工程**：围绕模型输出建设运行、分析、听审、追踪和交接工具。
- **系统定位能力**：沿音频、身份、事件和生成链路找原因，而不是把所有问题归结为大模型能力。
- **技术沟通能力**：让产品、算法与工程能够围绕同一条证据链讨论方案。

## 个人与团队的边界

这里展示的是我参与并整理的质量治理、实验分析、评测工具和方案交接工作。基础模型、完整音频处理、服务基础设施及记忆系统来自团队协作背景，不将整套系统表述为个人独立开发。各案例中会区分完成的分析/实验与提出的工程改进方向。
