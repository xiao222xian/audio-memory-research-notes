# 案例二：说话人归因——把“识别到声音”变成“有依据的叙事”

## 问题为什么不能只看声纹

最终卡片把别人的表达写成用户的经历，可能源于识别，也可能发生在识别之后。即使上游给出了候选和相似度，下游仍可能因为输入描述不完整、角色不清或叙事习惯，把所有内容统一写成“你”。

我沿着信息传播链路排查，关注身份线索在哪一步被弱化、丢失或过度确定。

```mermaid
flowchart LR
    A[说话人片段] --> B[身份候选与匹配线索]
    B --> C[事件中的角色表达]
    C --> D[生成器可见证据]
    D --> E[最终人称与行为归属]
```

## 我的排查步骤

### 1. 检查候选身份是否冲突

如果多个说话人同时被视为“疑似用户”，下游可能无法明确区分主体。此时需要检查候选的含义与使用规则，不能把“可能匹配”直接用作确定身份。

### 2. 检查下游实际收到什么

上游拥有的信息不一定都进入生成上下文。我关注下游是否只看见匿名编号和分数，是否缺少稳定角色描述，是否还能知道当前身份判断存在不确定性。

### 3. 对照具体叙事的归因

一张卡片可以包含多个陈述，每个陈述的归因依据并不相同。我的分析从“整张卡像不像用户经历”进一步拆到“这句话凭什么写成用户说过或做过”。

### 4. 将修复位置分开

如果是分段或匹配错误，应检查音频与身份处理；如果正确线索没有透传，应改进接口表达；如果线索充分但叙事仍越界，应检查生成约束和陈述校验。

## 我整理的方案方向

| 层次 | 改进方向 | 希望解决的问题 |
|---|---|---|
| 身份结果 | 区分确认身份与候选身份 | 避免把低置信候选直接当成主体 |
| 信息传递 | 保留角色描述和不确定性 | 避免摘要过程中身份信息丢失 |
| 生成约束 | 对确定的第二人称陈述要求证据 | 避免叙事风格覆盖归因判断 |
| 后验检查 | 核对陈述、片段与说话者的关系 | 检查输出是否超出输入支持范围 |

上述是已完成诊断后整理的改进方案，不把各层都描述为已经上线。

## 公开示例：我如何解释归因问题

以下为虚构场景，只用于说明方法：一段对话里，参与者甲描述一次旅行，用户乙仅作回应。如果摘要只留下旅行内容，生成器可能写成“你回忆起那次旅行”。

更稳妥的处理需要保留“谁在描述、谁在回应”，并约束最终叙事不能把甲的经历转给乙。这个例子说明：转录文本正确，仍然可能出现个人记忆错误。

## 产出与价值

我将问题从“是否需要更换声纹模型”扩展为一套跨层检查路径，形成身份透传与叙事归因的方案说明。这为后续工程改动提供了明确位置，也避免在缺乏定位时直接投入重训。

本案例体现我的系统分析能力：把感知模型输出、接口语义和生成行为作为连续链路看待。现存材料不支持宣称修复后的线上错误率，因此不提供推测的改善数字。
