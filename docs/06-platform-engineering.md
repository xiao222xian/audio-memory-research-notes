# 平台工程与研发工作台

## 平台覆盖的不只是模型调用

项目围绕算法与 Agent 建立了任务入口、队列消费、状态查询、实时事件、监控界面、调试产物和人工评测工具。它们连接业务调用、模型执行和问题排查，使团队能够从一次内容结果追溯到相关运行过程。

## 异步任务与状态管理

长耗时任务通过 Redis Streams 进入消费者组，Worker 控制并发执行。平台记录等待、运行、完成或失败状态，业务侧通过查询和事件订阅获得结果。输入流、输出流和状态存储分别承担分发、交付和查询职责。

异常处理包含确认消息、失败状态、死信队列和受控重试。已处理的业务失败与未捕获异常具有不同路径，避免失败任务无限堆积或在没有记录时反复执行。算法服务还包含调度与流维护组件，支持多阶段任务流转。

## Monitor 与可观测性

| 能力 | 研发和运维可以观察什么 |
|---|---|
| 任务统计与列表 | 运行量、状态和具体任务信息 |
| 实时事件 | 文本、工具调用、阶段进展与结束状态 |
| 执行元数据 | 模型、token、费用和错误信息 |
| 调试产物 | 大型输入输出及过程文件的定位依据 |
| 异常处理 | 死信查看、重试和任务恢复入口 |
| 指标与日志 | 服务行为、阶段耗时与问题排查线索 |

大体积调试产物与轻量状态分开保存，减少把完整上下文直接塞入状态存储的需要。监控界面是内部研发运维能力，对外材料仅展示功能，不公开管理入口和操作凭据。

## 算法研发工具链

固定样本进入批量运行后，结果按事件与时间对齐，生成指标和版本差异；人工通过听审页检查音频、转录、预测与标签，再导出反馈供后续比较。工具包含并发执行、失败重试、阶段缓存以及按目标步骤重跑。

听审页面支持按需加载音频、单播放器、自动保存、标签导入导出和错误分类。下游页面继续展示候选事件、生成或跳过、引用与最终内容，形成从片段到卡片的检查路径。

## 全项目系统地图

交互式系统地图覆盖音频到事件、身份流程、Agent 任务、记忆实验及运行基础设施。地图围绕数据流、模块职责和状态组织，帮助新成员和跨团队协作方理解系统。

这种可视化与运行监控用途不同：系统地图解释“系统如何组成”；Monitor 展示“任务如何运行”；听审与评测工具回答“输出是否符合目标”。三类界面共同构成研发工作台。

## 平台开发的工程价值

模型和业务策略持续变化时，平台提供稳定的任务契约、版本记录与观察入口。团队可以定位失败发生在数据准备、模型执行还是输出处理，基于证据比较方案，并将有效改动交接到相应模块。
