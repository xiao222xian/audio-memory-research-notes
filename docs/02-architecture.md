# 整体架构与数据流

## 系统职责

项目由音频算法服务、业务数据边界、Agent 内容服务、独立记忆实验、语音 Demo 和研发平台组成。业务后端提供事件与用户上下文，算法服务负责形成事件，Agent 服务负责消费材料并产生内容。记忆实验具有自己的写入与召回流程，不混入主 Agent 服务职责。

| 系统 | 主要输入 | 核心处理 | 主要输出 |
|---|---|---|---|
| 音频算法 | 录音、时间、已知身份线索 | 音频处理、转录、片段分析、聚合 | 音段、Fragment、Basic Event |
| 业务数据服务 | 用户资料与事件 | 数据管理与业务接口 | 用户上下文、事件查询结果 |
| Agent 内容服务 | 任务类型、版本、候选事件 | 准备上下文、模型执行、校验 | 卡片、信件、洞察等结构化结果 |
| 记忆实验 | 事件与转录资料 | 抽取、更新、检索、事件卡生成 | 分层记忆、实验内容与审计轨迹 |
| 实时语音 Demo | 问题、语音、独立记忆语料 | 路由、召回、推理、语音合成 | 语音回答、认知面板、会话记录 |
| 研发平台 | 运行状态、产物、人工反馈 | 监控、复核、回放、比较 | 定位证据、评测结果与交接材料 |

## 数据对象怎样逐步形成

**音段**保存时间范围、转录与说话人线索，是感知输出。**Fragment**在音段上增加场景、主题、摘要、连续性和内容来源等语义。**Basic Event**聚合多个相关片段，保留组成关系，形成适合业务消费的事件。**内容结果**则由 Agent 选择这些事件并生成，引用关系连接内容与证据。

这些对象不能互相替代：卡片是表达结果，事件是组织后的资料，音段是更接近原始输入的依据。问题排查需要能够从卡片逐层回到来源。

## 音频服务的六层工程结构

| 层 | 负责什么 | 设计收益 |
|---|---|---|
| 入口层 | 消费消息、CLI、调度与初始化 | 统一运行方式 |
| 业务编排层 | 下载、计算调度、存储和后续任务触发 | 集中管理副作用 |
| 流水线层 | 串联计算步骤 | 便于单独测试和阶段复用 |
| 算法单元层 | 音频、语音、信息提取和综合 | 支持模型与算法替换 |
| 数据接口层 | 对象存储、事件存储、业务接口 | 将外部系统与计算解耦 |
| 基础设施层 | 配置、模型调用、队列、日志与指标 | 为多个流程提供共用能力 |

数据模型独立定义各层之间的结构。计算流水线不直接承担上传、持久化和消息派发，业务编排负责将它们连接起来。

## 主服务与实验服务如何协作

主服务围绕稳定事件契约交付材料；实验通过独立备料、运行目录和输出记录开展验证。经过验证的方案可以整理为最小变更和回归依据，再决定是否进入主流程。公开架构展示这种协作方式，不公布内部部署拓扑、地址或凭据。

## 处理链路中的关键接口

1. **录音到算法**：时间、文件可用性与任务信息应完整。
2. **算法到事件**：语义与身份需要和片段边界共同保留。
3. **事件到生成**：明确候选集合、用户归属和引用对象。
4. **生成到展示**：区分生成、跳过、失败与无有效结果。
5. **实验到工程**：携带版本、输入条件、评测口径和适用范围。
